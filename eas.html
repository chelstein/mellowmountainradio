    What this is

    A standard, and a working implementation of it.

    Every EAS compliance record in the United States is a self-report. A station’s decoder logs what it believes it received and forwarded, and nothing independently corroborates it. Meanwhile the implementation guide the whole industry builds against — the ECIG CAP-to-EAS guide, which federal rules incorporate by reference — was published in May 2010, and the body that wrote it has not met since.

    OpenEAS is a read-only profile for observing what the alerting system actually did: which alerts were issued, what a station’s equipment did with them, and what its own recordings prove went to air. The server on this page is its reference implementation.

    It reads FEMA IPAWS-OPEN directly — the federal aggregator that carries civil-authority traffic like evacuation orders, AMBER alerts, and civil emergency messages. That is the difference between this and the dozen weather-API wrappers that exist: none of them touch the Emergency Alert System layer, and none of them speak SAME event or FIPS location codes.

    What it deliberately does not do

    It cannot originate, encode, relay, delay, or transmit an alert, and it has no connection to any air chain. That is an architectural commitment, not a phase-one limitation. It performs none of the functions in 47 CFR §§11.32, 11.33, or 11.56, so it sits outside the “EAS Software” category the FCC proposed in June 2026 — and the station’s certified decoder remains the authority on every forwarding decision. Anything the server derives is labelled as derived.

    It also contains no tone-generating code of any kind, and no EAS audio anywhere in its repository. A check enforcing that runs when the software is installed and again every time the service starts; if it ever fails, the service refuses to run.

    The tools

    Fifteen read-only tools on the public endpoint. Every one is marked readOnlyHint, and the naming is constrained to verbs that cannot be mistaken for a command to EAS equipment.

    • eas_get_active_alertsAny state, county, SAME code, NWS zone, lat/lon point, or the whole country
    • eas_get_ipaws_feedThe national IPAWS active window
    • eas_get_ipaws_alertOne full signed CAP alert, with an optional field-by-field audit
    • eas_find_alerts_for_pointWhich alerts contain a latitude and longitude
    • eas_get_alert_geojsonAn alert’s area as GeoJSON, ready to map
    • eas_get_alert_languagesEvery language variant, in full
    • eas_lookup_locationAll 3,295 SAME county codes, resolved to places
    • eas_explain_alertDecode a SAME header field by field, with rule citations
    • eas_get_event_codesThe §11.31 code tables as versioned data
    • eas_search_alert_historyHistorical Weather Service alerts
    • eas_search_archiveSearch the permanent archive of everything the server has observed
    • eas_verify_archiveVerify the archive’s hash chain end to end
    • eas_get_archive_statsHoldings and poll coverage — a quiet period and a period the poller was down are not the same thing
    • eas_backfill_historyIngest history from FEMA’s OpenFEMA archive
    • eas_get_conformanceVersion, declared regulatory position, source health

    Three further tools — playout status, as-run log, and the parity report that compares what the software decided against what actually aired — exist in the profile but run only on the studio machine, never in the cloud. They report unavailable here by design.

    Validation mode

    Every alert can be audited element by element, each check naming the rule or specification clause behind it, and reporting one of four results: pass, fail, absent, or unknown. A check that could not be completed is never reported as one that passed — so an alert whose signature we can see but have not cryptographically verified comes back indeterminate, not clean. That distinction is the point: the tool is meant to be checkable by someone who does not trust it.
